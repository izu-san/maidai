# 梨乃 生活連携基盤 仕様書

> 技術スタック・移行・実装フェーズの詳細は[生活連携基盤 詳細設計](梨乃_生活連携基盤_詳細設計.md)を参照する。

## 1. 目的

本仕様書は、既存の梨乃システムに「日常生活と連携するパーソナル生活エージェント機能」を追加するための設計・実装方針を定義する。

対象は単なるリマインダー機能ではなく、以下を統一的に扱える生活状態管理基盤とする。

- 日用品・消耗品の残量管理
- 家電・室内環境との連携
- PC状態監視
- 生活ルーティン把握
- メンテナンス周期管理
- 荷物・通販・定期購入管理
- ゴミ出し等の生活イベント管理
- 将来的な食料・冷蔵庫管理
- 手入力による家計簿（日本円の収支記録・月次集計）
- ゲーム・PC作業コンテキストとの統合
- 梨乃からの自然な声かけ
- 必要に応じたAgentによる自動処理

本機能は「LLMに状態を記憶させる」のではなく、状態管理を明示的なアプリケーションロジックとデータベースに持たせ、LLMは自然言語インターフェース・判断補助・会話生成を担当する。

## 2. 既存システム前提

以下は既に存在するものとして扱う。

- Memory
- Vision
- Agent
- Event Bus
- SwitchBot連携
- LLMとの会話インターフェース
- 永続化可能なDBまたはストレージ
- バックグラウンドタスク実行基盤
- イベント購読機構

既存機能は可能な限り再利用し、本機能専用の独立した巨大モジュールを作らない。

## 3. 設計方針

### 3.1 基本思想

生活関連の状態変化をすべて「イベント」として表現する。

例:

```text
laundry.completed
consumable.opened
consumable.purchased
consumable.adjusted
consumable.low
user.woke_up
user.went_out
user.returned_home
user.went_to_bed
room.co2_high
room.temperature_high
pc.started
pc.storage_low
pc.hardware_error
maintenance.completed
maintenance.due
package.arriving
trash.collection_due
```

各機能は Event Bus に対する Producer / Consumer として実装する。

---

### 3.2 責務分離

LLMに以下を直接やらせない。

- 残量計算
- 在庫数計算
- 消費ペース計算
- 日数計算
- 閾値判定
- 定期スケジュール管理
- デバイス制御ルールの最終判定
- 危険操作の実行可否判断

LLMが担当してよいもの:

- ユーザー発言からイベント候補を抽出
- 曖昧な表現の解釈
- イベントの自然言語化
- 複数コンテキストを使った会話生成
- 通知文・声かけ文の生成
- Agent行動候補の提案

## 5. 主要コンポーネント

## 5.1 LifeEvent

すべての生活イベント共通フォーマット。

```json
{
  "id": "uuid",
  "type": "laundry.completed",
  "timestamp": "2026-09-29T10:00:00+09:00",
  "source": "chat",
  "actor": "user",
  "confidence": 1.0,
  "payload": {
    "count": 1
  },
  "metadata": {
    "conversation_id": null,
    "device_id": null
  }
}
```

### 必須フィールド

| フィールド | 内容 |
|---|---|
| id | UUID |
| type | イベント種別 |
| timestamp | 発生日時 |
| source | chat / vision / switchbot / pc / system / manual 等 |
| payload | イベント固有データ |

### 任意フィールド

- actor
- confidence
- metadata
- correlation_id
- parent_event_id

---

## 5.2 ConsumableManager

日用品・消耗品の管理を担当する。

対象例:

- 洗濯洗剤
- 柔軟剤
- シャンプー
- コンディショナー
- ボディソープ
- 歯磨き粉
- ティッシュ
- トイレットペーパー
- ゴミ袋
- 猫用品
- 飲料
- 食洗機洗剤
- その他定期購入品

### 管理モデル

```json
{
  "id": "laundry_detergent",
  "name": "洗濯洗剤",
  "category": "household",
  "unit": "ml",
  "capacity": 900,
  "remaining": 625,
  "stock_unopened": 1,
  "usage_model": {
    "type": "PER_EVENT",
    "event": "laundry.completed",
    "amount": 25
  },
  "reminder": {
    "remaining_below": 150,
    "days_before_empty": 7,
    "stock_below": 1
  },
  "learning": {
    "enabled": true,
    "estimated_usage_per_event": 25,
    "observed_usage_per_event": null
  }
}
```

### 消費方式

```text
PER_EVENT
PER_DAY
MANUAL
REPLACEMENT
```

#### PER_EVENT
特定イベント発生時に一定量消費する。

例:

```text
laundry.completed -> 洗剤 -25ml
```

#### PER_DAY
1日あたり一定量消費。

実装状況: 実装済み。`usage_model: {"type": "PER_DAY", "amount": N}` を持つ品目を、`life.consumable.daily_consumed.v1`（日本時間の日付）で日次減算する。最終適用日を品目ごとに保持し、停止中の日数は次回起動時に追いつく。登録当日を起点とし、減算後は推定値として扱う。

#### MANUAL
ユーザー入力でのみ更新。

#### REPLACEMENT
正確な残量を持たず、交換日・使用開始日・寿命のみ管理。

## 5.3 在庫と使用中商品の分離

「現在使用中」と「未開封ストック」を分ける。

例:

```json
{
  "remaining": 420,
  "capacity": 900,
  "stock_unopened": 2
}
```

使用中が0になった場合:

```text
stock_unopened > 0
  -> stock_unopened -= 1
  -> remaining = capacity
```

ただし、実際に開封したか確認が必要なカテゴリでは自動遷移させず、`consumable.empty` を発火して確認待ちとする。

---

## 5.4 消費ペース学習

初期値は設定値を使用する。

例:

```text
洗濯洗剤: 25ml / 回
```

実測データが蓄積したら補正する。

例:

```text
900mlを30回で使い切った
-> 実測 30ml / 回
```

更新式は単純平均ではなく、EMA等を推奨。

例:

```text
new_estimate =
  old_estimate * 0.7 +
  observed_estimate * 0.3
```

実装時に係数は設定可能とする。

---

## 5.5 枯渇予測

以下を算出する。

- 残使用回数
- 平均イベント発生間隔
- 予想枯渇日
- 在庫込み予想枯渇日

例:

```text
残量 150ml
消費 25ml / 回
平均 2.5日に1回

-> 6回
-> 約15日
```

## 5.6 RoutineManager

ユーザーの生活イベントを管理する。

候補イベント:

```text
user.woke_up
user.went_out
user.returned_home
user.started_work
user.stopped_work
user.went_to_bed
pc.started
pc.locked
pc.unlocked
```

目的:

- 普段の生活パターン把握
- イベント発生頻度計算
- 通知タイミング最適化
- 「普段と違う状態」の検出

ただし、生活パターンから断定的な推測を行わない。

例:

```text
普段より就寝が遅い
```

は許可。

```text
今日は体調が悪いはず
```

のような推測は禁止。

## 5.7 EnvironmentManager

SwitchBot等から室内環境を取得する。

対象:

- 温度
- 湿度
- CO2
- 照明状態
- エアコン状態
- テレビ状態
- その他SwitchBotデバイス

例:

```text
room.temperature_changed
room.humidity_changed
room.co2_changed
room.co2_high
room.temperature_high
```

### 自動操作

原則:

```text
検出 -> 判断 -> 必要なら確認 -> 実行
```

安全な操作のみ自動化可能。

例:

- 照明OFF
- エアコンON/OFF
- テレビOFF

玄関ロックについては以下とする。

```text
施錠: 条件付きで許可
解錠: 禁止
```

## 5.8 PCMonitor

PC内部状態をイベント化する。

対象例:

- CPU使用率
- GPU使用率
- CPU温度
- GPU温度
- ディスク空き容量
- SMART
- Windows Event Log
- Docker container state
- WSL state
- サービス異常
- NVMeエラー
- ネットワーク状態

初期実装では、ディスク空き容量に加えて CPU 使用率（90%以上）とメモリ使用率（90%以上）を観測する。各閾値は連続2サンプルで初めてイベント化し、回復時にはカウンタをリセットする。

例:

```text
pc.storage_low
pc.cpu_high
pc.memory_high
pc.gpu_temperature_high
pc.service_failed
pc.hardware_error
docker.container_failed
network.latency_high
```

同一エラーの大量通知を避けるため、デバウンス・抑制機構を必須とする。

## 6. Notification Policy

生活AIでは「通知しすぎないこと」を最重要要件とする。

### Priority

```text
0: 記録のみ
1: 次回会話時に自然に触れる
2: 梨乃から能動的に話しかける
3: 即時通知
4: 自動対応 + 報告
```

例:

| 条件 | Priority |
|---|---:|
| CO2 1050ppm | 1 |
| CO2 1600ppm | 2 |
| SSD空き容量15% | 1 |
| NVMe hardware error | 3 |
| 通常時間帯の照明ON | 0 |
| 外出中かつ深夜の照明ON | 2 |

---

## 7. NotificationRouter

通知前に必ず以下を確認する。

- 同じ内容を最近通知したか
- ユーザーが現在忙しい可能性
- Vision上でゲーム・作業中か
- 緊急度
- イベントの確信度
- Quiet Hours
- 既に解決済みか
- 他イベントとまとめられるか

### 通知抑制

最低限:

```text
cooldown
deduplication
aggregation
quiet_hours
acknowledged
resolved
```

をサポートする。

## 8. Context統合

梨乃が声をかける際は、イベント単体で発言を生成しない。

使用可能なコンテキスト:

- 現在イベント
- 関連する生活状態
- Memory
- Vision
- 現在時刻
- PC状態
- SwitchBot状態
- 直近の会話
- 直近の通知履歴

例:

```text
consumable.low
+
在庫0
+
普段の消費ペース
+
次回配送予定なし
```

から、

```text
「洗剤、今のペースだとあと1週間くらいでなくなりそうです。ストックもないですよ」
```

のような発話を生成する。

## 9. LLM Tool / Function Interface

LLMから生活状態を直接更新させない。Agent 所有の private stdio Life MCP を介し、固定された domain verb を loopback Life API に送る。

LLMは明示的Toolを呼ぶ。

例:

```text
life.record_laundry_completed()
life.get_consumable_state()
life.list_consumables()
life.list_low_stock_items()
life.adjust_consumable()
life.record_purchase()
life.record_opened_item()
life.register_consumable()
life.deactivate_consumable()
```

任意の event type や payload を引数に取る汎用 MCP tool は提供しない。Life API が検証、状態更新、Outbox 追加を同一トランザクションで行う。PC 監視のイベントは引き続き Life 基盤の consumer / notification router で扱い、会話 UI への自動配送は別接続が必要である。

## 14. イベント履歴

状態変更は必ず履歴を残す。

例:

```text
2026-09-01 purchased 900ml
2026-09-01 opened
2026-09-02 laundry.completed -25ml
2026-09-05 laundry.completed -25ml
...
```

これにより、

- 誤更新の修正
- 消費ペース分析
- 将来的なグラフ表示
- LLMからの説明
- 異常値検出

が可能。

## 15. 手動修正

推定残量は必ず手動修正可能にする。

例:

```text
「洗剤たぶん半分くらい」
```

のような入力は

```text
estimated = true
remaining_ratio = 0.5
```

として扱えるようにする。

厳密値と推定値を区別する。

---

## 16. Safety / Permission

Agentによる行動は権限レベルを持たせる。

```text
READ_ONLY
SAFE_ACTION
CONFIRM_REQUIRED
FORBIDDEN
```

例:

| 操作 | 権限 |
|---|---|
| CO2取得 | READ_ONLY |
| 照明OFF | SAFE_ACTION |
| エアコンON | SAFE_ACTION or CONFIRM_REQUIRED |
| 商品購入 | CONFIRM_REQUIRED |
| 定期便キャンセル | CONFIRM_REQUIRED |
| 玄関施錠 | CONFIRM_REQUIRED |
| 玄関解錠 | FORBIDDEN |

自動購入は初期実装では禁止。

## 22. 実装時の禁止事項

以下は禁止。

- LLM Memoryだけで残量管理する
- LLMプロンプト内に在庫状態を直接保持する
- 消費量を毎回LLMに計算させる
- イベント名を各所に文字列ベタ書きする
- 通知クールダウンなし
- 同一イベントの無限通知
- 外部デバイス操作をLLM判断だけで即時実行
- 玄関解錠
- 自動購入
- 定期購入の自動キャンセル
- 既存Event Busを無視した独自メッセージ基盤作成
- 既存Agentとは別の巨大Agentフレームワーク追加

## 24. 最終的な目標

梨乃を、

```text
命令されたら動くAI
```

から、

```text
ユーザーの生活・家・PC・作業状況を

必要な時だけ自然に反応し、
安全な範囲で行動できるAI
```

へ発展させる。

本機能は個別の便利機能ではなく、今後の日常生活連携機能すべての土台となる「Life Context / Life Event Platform」として設計すること。
