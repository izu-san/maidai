# 梨乃 生活連携基盤 詳細設計

> ステータス: Phase 5 実装済み  
> 対象: [`梨乃_生活連携基盤_仕様書.md`](梨乃_生活連携基盤_仕様書.md) の Phase 1 以降  
> 最終更新: 2026-09-29

## 1. 決定事項

生活連携基盤は、次の責務分離で構築する。

| 領域 | 採用技術 | 正本となる責務 |
| --- | --- | --- |
| ドメインAPI・ルール | Python 3 / FastAPI / Pydantic v2 | 入力検証、状態遷移、ポリシー判定 |
| 永続化 | PostgreSQL | 状態、完全な履歴、設定、承認、通知履歴、Outbox |
| DBアクセス | SQLAlchemy 2 / psycopg / Alembic | 非同期アクセスと再現可能なスキーマ変更 |
| 非同期イベント | NATS JetStream | プロセス間配信、再配信、consumer進捗、短中期リプレイ |
| Python NATS client | `nats-py` | producer / durable pull consumer |
| TypeScript NATS client | `nats` | Node側のproducer / bridge |
| 契約 | JSON Schema + Pydanticモデル | イベント互換性・入力検証 |
| 運用 | Docker Compose | PostgreSQL / NATSのローカル閉域運用 |

### 1.1 採用しないもの

- **SQLite**: 個人利用には便利だが、既存の複数プロセス構成と今後のSwitchBot・PC・Vision・外部連携の共有状態基盤には採用しない。
- **PostgreSQL `LISTEN` / `NOTIFY` 単独**: DB変更通知の補助としては使えるが、consumerごとの進捗、再配信、未読管理、リプレイの責務を持たせない。
- **Core NATS 単独**: 接続中の購読者だけに届くため不採用。必ずJetStreamを有効化する。
- **Kafka / Redpanda**: 大量ログ・大規模分析向けであり、現時点の単一家庭環境には運用負荷が過大。
- **RabbitMQ**: ジョブキュー中心なら有力だが、複数consumerによる生活イベント購読・IoT・subject設計の一貫性ではNATSが適する。
- **Temporalの初期導入**: 長期承認待ちや複数段階自動化が実際に複雑化するまで導入しない。NATSの代替ではない。

## 2. アーキテクチャ

```text
Chat / SwitchBot / PC Monitor / Vision / Manual UI
                     |
                     v
        Life API / Event Ingestion (FastAPI)
                     |
             validation + policy
                     |
                     v
  PostgreSQL transaction ------------------+
  - life_events                            |
  - current-state read models              |
  - outbox_events                          |
                     |                     |
                     v                     |
       Outbox Publisher (durable worker)   |
                     |                     |
                     v                     |
             NATS JetStream                |
              |             |              |
              v             v              v
      NotificationRouter  Agent adapter  Node bridge/UI
              |             |              |
              +-------------+--------------+
                            |
                            v
                  PostgreSQL (idempotent writes)
```

### 2.1 不変条件

1. PostgreSQLが生活状態と監査履歴の唯一の正本である。
2. NATS JetStreamはイベント配信・再処理用であり、状態を直接更新する唯一の経路にはしない。
3. 状態を変える全操作は、同一DBトランザクションで`life_events`、read model、`outbox_events`を書き込む。
4. LLM、Vision、外部イベントは候補を送るだけであり、Pydantic検証とドメインルールを通過しなければ状態を変えない。
5. consumerは少なくとも一度の配信を前提に、イベントIDで冪等に処理する。
6. Agentによる実世界操作は既存のMCP・Policy・Approval・Audit経路を維持し、イベント受信だけで実行しない。

## 3. PostgreSQL設計

### 3.1 基本方針

- DB時刻は`TIMESTAMPTZ`で保存し、表示時だけ`Asia/Tokyo`へ変換する。
- UUIDはアプリケーション側で生成する。イベントIDは全経路で不変とする。
- 可変payloadは`JSONB`、検索・整合性が必要な値は通常カラムに分離する。
- Alembic migrationのみでスキーマ変更する。手作業DDLは禁止する。

### 3.2 初期テーブル

| テーブル | 主な列 | 用途 |
| --- | --- | --- |
| `life_events` | `id`, `type`, `occurred_at`, `source`, `actor`, `confidence`, `correlation_id`, `payload` | 改ざんしないイベント履歴 |
| `consumables` | `id`, `name`, `category`, `unit`, `capacity`, `remaining`, `stock_unopened`, `estimated`, `version` | 消耗品の現在状態 |
| `consumable_history` | `id`, `consumable_id`, `event_id`, `before`, `after`, `reason` | 消耗品状態の説明可能な差分 |
| `notification_history` | `id`, `dedupe_key`, `event_id`, `priority`, `status`, `sent_at`, `acknowledged_at`, `resolved_at` | 抑制・確認・解決状態 |
| `outbox_events` | `id`, `subject`, `schema_version`, `payload`, `created_at`, `published_at`, `attempts`, `last_error` | DBとNATSを結ぶ送信待ちイベント |
| `processed_events` | `consumer_name`, `event_id`, `processed_at` | consumerごとの冪等性 |
| `life_settings` | `key`, `value`, `version`, `updated_at` | YAML初期値を上書きする将来設定 |

Phase 2で`maintenance_items`、`maintenance_history`、`routine_stats`を、Phase 3で`environment_state`、`pc_state`を追加する。

### 3.3 Outbox

状態変更のトランザクションでは、対応するイベントを必ず`outbox_events`にも追加する。

```text
BEGIN
  INSERT life_events ...
  UPDATE / INSERT consumables ...
  INSERT consumable_history ...
  INSERT outbox_events (subject, payload) ...
COMMIT

Outbox Publisher
  -> 未送信行をロックしてJetStreamへpublish
  -> publish ACK受領後にpublished_atを設定
```

- Publisherの停止・NATS停止中も、未送信行はDBに残る。
- ACK前にプロセスが落ちた場合は再発行されうるため、consumerの冪等性を必須とする。
- 失敗回数・最終エラーを保持し、上限超過は`system.outbox_failed.v1`を発行して運用者に見えるようにする。

## 4. NATS JetStream設計

### 4.1 Stream

| Stream | subjects | storage / retention | 目的 |
| --- | --- | --- | --- |
| `RINO_LIFE` | `life.>` | file / limits | 生活ドメインの状態変化 |
| `RINO_DEVICE` | `switchbot.>`, `pc.>`, `vision.>` | file / limits | デバイス・観測イベント |
| `RINO_SYSTEM` | `system.>`, `agent.>` | file / limits | 運用・Agentライフサイクル |

初期値は単一ノード・file storageとする。単一PC構成では高可用化は得られないため、PostgreSQLバックアップと復元確認を優先する。将来別ホストへ移す場合にのみ、NATS/JetStreamを3ノードクラスタ化する。

### 4.2 Subject命名とバージョン

形式は`<domain>.<action>.v<major>`とする。

```text
life.consumable.purchased.v1
life.consumable.adjusted.v1
life.consumable.low.v1
switchbot.co2_changed.v1
pc.storage_low.v1
system.outbox_failed.v1
```

- actionは過去形または状態変化を表す小文字`snake_case`とする。
- 破壊的なpayload変更は新subject（`v2`）を追加する。既存subjectの意味を変更しない。
- `life.*`は状態変更済みの事実、`*.command.*`は将来の明示的コマンド用とし、混在させない。

### 4.3 Consumer規約

- durable pull consumer、explicit ack、明示的な`ack_wait`・`max_deliver`を使用する。
- consumer名は機能名で固定する。例: `life-notification-router-v1`。
- 処理開始時に`processed_events`を確認し、既処理ならackのみ行う。
- DB書込み成功後にackする。失敗時はackせず再配信させる。
- 永続的失敗は無限再試行しない。上限到達後にDLQ相当の`system.consumer_failed.v1`を出し、原因イベントIDを保持する。

## 5. イベント契約

### 5.1 共通Envelope

NATSのmessage bodyは次のJSONとする。subjectはmessage外部のNATS subjectを正とし、bodyの`type`はsubjectと一致しなければならない。

```json
{
  "id": "018f0d48-4c1b-7b33-b21a-0e3da0c9b401",
  "type": "life.consumable.purchased.v1",
  "occurred_at": "2026-09-29T10:00:00+09:00",
  "source": "chat",
  "actor": "user",
  "confidence": 1.0,
  "correlation_id": "conversation_abc",
  "causation_id": null,
  "payload": {}
}
```

`id`、`type`、`occurred_at`、`source`、`payload`は必須。`confidence`は`0.0`から`1.0`まで。秘密情報、認証情報、無加工の画面・会話全文はpayloadに入れない。

### 5.2 Phase 1 payload

| subject | 必須payload | 効果 |
| --- | --- | --- |
| `life.laundry.completed.v1` | `count: integer (>=1)` | 設定に従い消耗品を減算 |
| `life.consumable.purchased.v1` | `item_id`, `quantity (>=1)` | 未開封在庫を加算 |
| `life.consumable.opened.v1` | `item_id` | 在庫を1減らし、使用中残量をcapacityへ設定 |
| `life.consumable.adjusted.v1` | `item_id`, `remaining`, `estimated` | 手動補正 |
| `life.consumable.low.v1` | `item_id`, `remaining`, `threshold` | 通知候補。状態変更はしない |
| `life.consumable.empty.v1` | `item_id` | 確認または補充フローの候補 |

### 5.3 Schema管理

```text
contracts/
  life-envelope.v1.schema.json
  life/
    consumable-purchased.v1.schema.json
    consumable-adjusted.v1.schema.json
  switchbot/
    co2-changed.v1.schema.json
```

- PydanticモデルとJSON Schemaの整合性をCIで検証する。
- TypeScript側はJSON Schemaから型を生成するか、少なくとも受信時にSchema検証する。
- Schemaの後方互換性テストを追加する。

## 6. 既存コンポーネントとの統合

### 6.1 SwitchBot（Phase 1）

SwitchBotは既存連携済みのため、生活基盤の後回しにはしない。

```text
SwitchBot MCP
  - Agentからの同期的な状態取得・実操作
  - 既存Policy / Approval / Auditを維持

SwitchBot Event Producer
  - センサー値・デバイス状態の変化をNATSへ発行
  - PostgreSQLへ最新観測状態と履歴を保存
```

操作と観測を分離する。NATSイベントを受けただけで照明・エアコン等を直接操作してはならない。操作は必ず安全ポリシーを通したMCP commandとして実行する。

### 6.2 既存Node Event Bus

既存`rino_event_bus`はプロセスローカルの即時通知として残すが、生活状態の正本経路には使わない。

移行中はBridgeを用意する。

```text
既存 SwitchBot / Vision producer
  -> Node Event Bus
  -> NATS publisher bridge

NATS device event
  -> 必要なNode UI consumer
  -> Node Event Bus（UI用途のみ）
```

- Bridgeは`event.id`を維持し、自己発行イベントを再転送しない。
- `rino_event_bus/src/agent-event-bridge.ts`のHTTP Bridgeは既存API互換のために当面維持する。
- `/events`の許可正規表現・Bridge購読対象は、NATS移行後に`life.*`を安易に追加しない。生活状態更新はLife API専用の認証済みendpointへ送る。

### 6.3 Agent / LLM

LLMは以下の名前付きMCP toolだけを利用する。Life MCP は Agent が所有する stdio 子プロセスであり、`RINO_LIFE_API_URL` の loopback Life API だけを呼ぶ。SQL、NATS publish、任意イベント subject / payload、SwitchBot操作を直接公開しない。

```text
life.record_laundry_completed(count)
life.get_consumable_state(item_id)
life.list_consumables()
life.list_low_stock_items()
life.adjust_consumable(item_id, remaining, estimated)
life.record_purchase(item_id, quantity)
life.record_opened_item(item_id)
life.register_consumable(...)
life.deactivate_consumable(item_id, reason?)
```

Life API はイベント型ごとの Pydantic validation を行う。登録・削除は Agent ポリシーで毎回承認を要求する。Vision 由来の候補や曖昧な会話は、この MCP による状態更新へ変換しない。

## 7. NotificationRouter

通知は別consumerとして実装する。通知候補を受け、`notification_history`をトランザクションで参照・更新してから送信する。

必須判定項目:

- `dedupe_key`とcooldown
- 未解決・未acknowledgedの既存通知
- quiet hours
- priority（0〜4）
- confidence
- 直近の会話・作業・ゲーム状況
- 複数候補のaggregation

同じ`life.consumable.low.v1`が再配信または再評価されても、同一`dedupe_key`の通知を繰り返さない。Priority 3以上以外は、原則として即時にAgentを起動せず、通知ルーターが定めたタイミングで自然な会話候補にする。

## 8. セキュリティと運用

- PostgreSQLとNATSはloopbackまたはDocker internal networkだけで公開する。外部公開しない。
- 開発・本番相当でNATS account/userを分離し、subject publish/subscribe権限を最小化する。
- DB資格情報とNATS credentialはコード、YAML、イベントpayload、ログへ書かない。
- PostgreSQLは日次論理バックアップ、NATS JetStream volumeは定期バックアップ対象にする。
- 復元テストを定期実施し、DB復元後にOutbox未送信イベントを安全に再発行できることを確認する。
- OpenTelemetry等の導入は後続とするが、最低限`event_id`、`correlation_id`、subject、consumer、処理時間、失敗理由を構造化ログに含める。

#### 消耗品カタログの運用

### Phase 4 — PC / Vision / Routine

#### Phase 5 運用規約

- `maintenance_items` / `maintenance_history`、`trash_schedules`、`deliveries`、`subscriptions`をmigration `20260929_06`で追加する。状態変更は`life.maintenance.completed.v1`、`life.trash.collected.v1`、`life.package.updated.v1`、`life.subscription.updated.v1`だけを受け付け、`life_events`とOutboxを同一トランザクションで記録する。
- `tools/Backup-RinoLife.ps1`を日次タスクとして実行し、DBのcustom-format論理バックアップとJetStream volume archiveを作成する。`tools/Test-RinoLifeRestore.ps1`を月次タスクとして実行し、`pg_restore --list`でバックアップを検査する。実DBへの復元は停止済みの使い捨てDBに限る。
- 保持期間は、監査対象の`RINO_LIFE`を365日、再取得可能な観測・システムイベントを90日とする。DBの`life_events`は日次バックアップを正本として18か月保持後に同じ形式の論理アーカイブへ移す。容量・復元時間を月次記録し、90日間の実測後に上限を見直す。
- Temporalは、承認待ちが複数日をまたぎ、再開・取消・補償の状態遷移を3段階以上持つワークフローが2件以上発生した時だけ再評価する。それまではPostgreSQLの状態と明示的な期限ジョブで管理する。
- MQTT / Home Assistant / Calendarはそれぞれ`mqtt.device_observed.v1`、`home_assistant.state_changed.v1`、`calendar.event_changed.v1`に正規化する。adapterはallowlistとJSON Schema検証だけを担い、状態変更・実世界操作を直接行わない。

完了条件: 新しい生活連携を、既存の状態・安全・監査・通知の規約を破らずに追加できる。

## 10. 受け入れ基準

1. NATSまたはconsumerの再起動中に発生したイベントが、DB Outbox経由で最終的に配信される。
2. 同一イベントの再配信を何度受けても、消耗品残量・通知・履歴の意味的な更新は一回だけである。
3. PostgreSQL復元後、未送信Outboxを再発行してもconsumer冪等性が維持される。
4. SwitchBotの観測イベントは記録できるが、観測だけで危険操作は実行されない。
5. LLMは許可されたMCP tool以外で生活状態を変更できない。
6. 仕様書のMVP受け入れテストCase 1〜7、およびOutbox/再配信/通知抑制の統合テストがCIで通る。
